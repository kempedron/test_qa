# Bug-репорт: API Students (http://194.87.126.16)

## Сводка
При тестировании блок operations со студентами (GET, POST, PUT, DELETE) выявлены следующие дефекты. Во всех случаях API возвращает HTTP 200 с телом ответа, содержащим поле `"status": 0`, вместо соответствующих HTTP 4xx кодов.

---

## Баг #1 — GET /student/{student_id}: не возвращает созданного студента

**Ожидаемый результат:** после успешного создания студента запрос GET по его `id` должен возвращать данные студента со статусом `1`.

**Фактический результат:** GET /student/{id} возвращает `200 OK` с телом:
```json
{"message":"Student not found","status":0}
```
хотя студент только что создан тем же клиентом (POST вернул его `id`).

**Шаги воспроизведения:**
1. POST /student с валидным телом → получаем `student.id`.
2. GET /student/{student.id} → `200 {"message":"Student not found","status":0}`.

**Серьезность:** Высокая. **Приоритет:** Высокий.

---

## Баг #2 — PUT /student/{student_id}: обновление не работает

**Ожидаемый результат:** PUT по существующему `student_id` обновляет данные и возвращает `"status":1`.

**Фактический результат:** PUT возвращает `200 OK` с телом:
```json
{"message":"Student not found, student not updated","status":0}
```
даже для студента, который существует (подтверждено GET до попытки обновления).

**Серьезность:** Высокая. **Приоритет:** Высокий.

---

## Баг #3 — DELETE /student/{student_id}: удаление не работает

**Ожидаемый результат:** после DELETE студент больше не доступен через GET.

**Фактический результат:** DELETE возвращает `200 {"message":"Student deleted successfully","status":1}`, но последующий GET /student/{id} всё ещё возвращает данные студента.

**Серьезность:** Высокая. **Приоритет:** Высокий.

---

## Баг #4 — DELETE /student/{student_id}: удаление несуществующего студента

**Ожидаемый результат:** при удалении несуществующего `student_id` API должен вернуть ошибку (HTTP 404 / статус 0).

**Фактический результат:** DELETE /student/999999 возвращает `200 {"message":"Student deleted successfully","status":1}`.

**Серьезность:** Средняя. **Приоритет:** Средний.

---

## Баг #5 — GET /student/{student_id}: несуществующий студент возвращает 200

**Ожидаемый результат:** GET по несуществующему `id` должен возвращать HTTP 404.

**Фактический результат:** GET /student/999999 возвращает `200 OK` с телом `{"message":"Student not found","status":0}`.

**Серьезность:** Средняя. **Приоритет:** Средний.

---

## Баг #6 — POST /student: некорректный запрос возвращает 200

**Ожидаемый результат:** при отсутствии обязательных полей или невалидном значении (например, `gender`) API должен возвращать HTTP 400.

**Фактический результат:**
- POST с отсутствующими полями → `200 {"message":"Wrong JSON, student not created","status":0}`.
- POST с невалидным `gender` → `200 {"message":"Wrong gender, student not created","status":0}`.

**Серьезность:** Средняя. **Приоритет:** Средний.

---

## Общее наблюдение

API systémно использует HTTP 200 для ошибочных сценариев, информируя об ошибке только полем `"status": 0` в теле ответа. Это не соответствует REST-конвенциям (ошибки клиента/сервера должны отдавать 4xx/5xx), усложняет автоматическую обработку ответов и маскирует реальные сбои.
